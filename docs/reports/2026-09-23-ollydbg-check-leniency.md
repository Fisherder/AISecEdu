# 让破解判定更宽松、更智能（2026-09-23 第二轮）

上一轮把判定从"5 组固定字节"改成"行为 + 最小改动"，学生已经能按文档方法过关。本轮继续放宽并加入
**动态分析**，让学生用任何**真正有效**的改法都能过，同时把"为什么不过"讲清楚。

## 一、放宽了什么

| 项目 | 上一轮 | 现在 |
| --- | --- | --- |
| 可改范围 | 硬编码 RVA 0x15E2–0x1658 | **靠模拟执行自动发现**：把正确密码和错误密码各跑一遍，凡是执行到的指令（含入口、比较、跳转、返回）都算认证代码，两侧再各留 16 字节余量 |
| 改动字节上限 | 8 字节 | **40 字节**（允许替换多条指令、写长跳转等） |
| 可接受的方法 | 反转条件 / NOP / 无条件跳转 / 改比较 | 以上 + **函数入口直接返回成功**（`xor eax,eax; ret` 这类"永远成功"改法）+ 其它把错误密码引到成功分支的等价改法 |
| 等价编码 | `sub eax,eax`、`mov eax,0` 等已接受 | 继续接受，且分类按**语义**而不是字节模式 |
| 方法种类判定 | 5 类 | 反转条件 / 去掉条件 / 强制跳转 / 强制比较 / 入口直接成功 / 跳转重定向 / 自定义（两份必须不同类） |

## 二、智能在哪里

1. **动态识别认证代码**：不写死地址。判定器在模拟器里跑正确/错误两次注册，收集真正执行到的指令地址，
   换算成文件偏移得到"可改窗口"。换编译器、换版本都不会误判。
2. **按程序自己的成功约定判分**：判定器从原始代码的 `test eax,eax` + `jne 失败分支` 推出"EAX=0 即成功"，
   于是"函数提前 return 0"这种改法也能被正确判定为成功，而不是被判"跑不到分支"。
3. **指令级诊断（capstone 反汇编）**：报错时直接给出改动的字节和地址，例如
   > Method 1（method1.exe）：补丁没有生效：错误密码仍然走到失败分支。你把 0x40161E 改成了跳向 0x401637，
   > 而那正是失败分支；应该改成不跳（落到成功分支）或跳向成功分支 0x401620。
   > （检测到的改动：0x40161E 75 17 → eb 17）

   以及最常见的两种失误：
   > 这份文件与 crackme-original.exe 完全相同，还没有做任何修改；请确认改动已保存到这个文件名
   > 改动范围超出了认证判断代码：共改动 12 字节，其中 4 字节在认证代码之外……

4. **两份必须"不同种类"**：同一类改法（例如 `xor eax,eax` 与 `sub eax,eax`）会明确提示
   "两份文件用的是同一种方法（force-comparison），请换一种不同种类的改法"，而不是笼统报错。
5. 反汇编库缺失时自动退化为字节级判定（不会因为环境差异直接报错）。

## 四、不影响学生环境

- 判定器在**镜像**里，学生**下次启动/点「重启」**即生效；「重启」只重建容器，**保留客户机磁盘**：
  实测重启后 `probeMask` 仍为 15（三份副本都已改动、flag.txt 仍在），学生进度零丢失。
- 本轮改动只在 `verifier.py`（判定逻辑），不写学生磁盘、不动数据库。
- 已在运行的学生容器不会被自动重启；我这次只重启了自己的测试账号 `user_7239`，
  同时在线学习的 `user_7077`、`user_7129` 未受任何影响（重启前后 uptime 连续）。


## 五、顺带修掉一个真实的"冤枉"来源：串口传输丢字节

客户机把三份文件通过 **COM1 串口**（无流控、无校验）发给判定器。实测（在容器里删掉文件中间
1 个字节模拟丢包）会导致后面全部错位，判定器看到"改动 3931 字节"，于是把一份**完全正确**的提交拒掉——
学生只会看到一句莫名其妙的"改动范围超出"，怎么改都过不了。

现在判定器会**自动识别并修复这种错位**：尾部与原始文件按 ±1/±2 字节对齐时，判定为传输丢字节，
重新插回缺失的字节（零区间导致插入点不唯一时，取"与原始文件差异最小"的那个），
修复记录写进判定结果（`transferRepaired`）。实测：

| 场景 | 结果 |
| --- | --- |
| 正常传输 | 通过 ✓ |
| method1 丢 1 字节 | **通过**（自动修复，repaired=['method1.exe']）✓ |
| method2 丢 1 字节 | **通过**（自动修复）✓ |
| 两份各丢 1 字节 | **通过**（两份都自动修复）✓ |

修复只在"疑似错位"时触发（改动字节数远超正常补丁且尾部对齐），不会把乱改的提交放过：
上面 10 组判定矩阵在加入修复后仍然全部符合预期（乱改一个字节、未改动、同一种方法等依旧被拒）✓。
