# 教学任务跑了一小时没结果：分层定位与修复（2026-09-21）

## 结论先说：不是浏览器/网络层，而是"生成 → 校验 → 定向修复"的重试循环 + 超时上限过大

## 现象与定位过程

任务：`生成一个交互式的虚拟内存原理的介绍…3D 展示`，界面显示「生成核心内容 60% · 已用时 1 小时 4 分」。

数据库 `teaching_jobs` 里的真实状态：

```
id       job_ce32f3db8d584199bf3e320cdd17cf2d
kind     artifact.materialize      （把方案落成可用的实训作品）
status   RUNNING
stage    generating
attempt  5 / 5                     ← 已经跑到第 5 次尝试
created  14:05:05   updated 15:15:17
```

worker 日志里最后一次失败的原文：

```
ERROR Teaching job job_ce32f3db... failed
RuntimeJobError: GENERATION_REPAIR_REQUIRED:
本轮内容未通过结构、交互或教学检查，需要继续定向修复；尚未发布为完成作品。
```

对比：9 月 17 日同类型任务（`job_6fa80ff7…`）**7 分半**就完成了 → 因此这次不是"模型慢"，而是**反复生成都不通过校验**。

### 三层的实际状况

| 层 | 状况 |
| --- | --- |
| 前端 / 网络 | 正常。前端一直在按任务状态刷新，只是任务本身没有终态 |
| 任务调度层（jobs.py） | **问题所在**：① `artifact.materialize` 允许 5 次尝试；② 恢复机制还会把尝试次数继续往上加；③ 单次调用的读超时对"课件/仿真"类任务放宽到 **35–40 分钟**，于是最坏情况 = 5 × 40 分钟；④ 期间界面只显示百分比，不显示"第几次尝试/正在定向修复"，用户无从判断 |
| 生成与校验层 | 模型多次产出的仿真内容**未通过平台的结构/交互/教学检查**，每次都进入"定向修复"再失败，形成循环 |

## 本次修复

1. **单次调用超时加上限**：新增 `LONG_JOB_READ_TIMEOUT_SECONDS`（默认 **600 秒 = 10 分钟**，
   可用环境变量 `TEACHING_LONG_JOB_READ_TIMEOUT_SECONDS` 调整，范围 600–2400）。
   课件/仿真类任务不再享受 35–40 分钟的单次预算。
2. **尝试次数上限收紧**：新增 `MAX_JOB_ATTEMPTS`（默认 **3**，可用 `TEACHING_MAX_JOB_ATTEMPTS` 调整），
   并且恢复机制里的"自动加次数"也被同一上限约束（原来 `max_attempts = max(max_attempts, attempt_count+1)` 可无限增长）。
3. **立即解堵**：把卡住的那条任务置为失败并写明原因：
   「执行时间超过上限（多次定向修复仍未通过结构/交互/教学检查），已终止；请调整要求后重试。」
   这样界面上不再是无休止的进度条，而是明确的失败与原因，用户可以直接改了重来。
4. 已重启 `teaching-worker` / `teaching-interactive-worker` / `teaching-authoring-worker(-2)` 与 `ctfd`。

修复后的最坏耗时：**3 次 × 10 分钟 ≈ 30 分钟**（原来可达 3 小时以上），且必然进入终态。

## 还没做、建议继续做的（需要你点头）

1. **把"第 N/M 次尝试、正在定向修复"显示到界面上**（现在只有百分比），让长任务可见、可判断、可取消；
2. **给这类生成加一个用户可点的「取消任务」**（后端已有 `canceled` 字段，尚未在界面暴露）；
3. **进一步压缩校验循环**：例如同一类结构/交互错误连续出现 2 次就停止重试并给出"具体缺什么"的清单，
   而不是把同一轮修复反复跑满；必要时把"定向修复"的提示词收紧到只改被判错的那几项。

## 追加：真正的效率瓶颈在质量闸门，而不是超时

按"不要用超时上限、要成功且快、校验可以放松"的要求重新定位：

1. `GENERATION_REPAIR_REQUIRED` 来自 **agent-runtime 的质量闸门**：
   - `services/agent-runtime/lib/server/cinematic-generation.ts`（`CinematicQualityError`，第 891 行起）
   - `services/agent-runtime/lib/server/cinematic-revision.ts`（局部修订未通过验证即整体放弃，第 116 行）
   平台侧只是把它归类为"质量问题、可重试"。
2. 候选生成里已经写着 `maxRepairs`（默认 2，最多 3）以及"确定性兜底候选"；
   但对**仿真/3D 场景**这类长内容，每一轮修复都要重新跑一次长时间生成，
   多轮叠加就是用户看到的 1 小时以上；而最终仍然抛错，等于既慢又失败。
3. 因此正确的优化方向（已与用户口径一致）：
   - **接受最好的一版**：第一轮修复后仍有问题就带着"警告清单"发布，而不是失败重来；
   - **硬校验只保留完整性**（JSON 可解析、schema 合法、引用的 id 存在、页面数量在区间内）；
     版式重叠、字号下限、教学措辞、重复候选等降级为**警告**；
   - **修复轮数上限 1**，且修复只改被判错的字段，不再整篇重写；
   - 候选并行度从 2 提到 3–4，压缩墙钟时间。
4. 已回退上一轮"10 分钟硬上限"为 1800 秒兜底（不作为效率手段），避免简单超时推高失败率。

### 实现位置与风险

上述改动都在 agent-runtime 的 TypeScript 里，需要**重建运行时镜像**；
当前环境访问不到 Docker Hub（拉不到 `node:22-alpine`），只能像之前那次技能改动一样
**离线打运行时编译产物的补丁**（可行，但属于高风险改动，需要一次真实生成做验证，约 10 分钟）。
