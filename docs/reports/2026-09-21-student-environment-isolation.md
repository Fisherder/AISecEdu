# 学生实验环境隔离性核查（2026-09-21）

## 结论

每个学生启动的确实是**独立容器**，并且在容器、网络、文件、客户机磁盘、平台接口五个层面都做了隔离；
跨学生访问在实测中全部被拒绝。唯一需要知道的一点：**工作区的签名 URL 本身是一张"通行证"**
（谁拿到完整 URL 谁就能打开那个桌面），它不可猜测、随环境重建失效，但不绑定会话。

## 隔离维度与实测

| 维度 | 机制 | 实测结果 |
| --- | --- | --- |
| 容器 | 每人一个容器，名字 `user_<user_id>`，由会话用户解析容器名 | 两个学生分别得到 `user_7208`、`user_7064`，容器 ID 不同 |
| 主目录 | `/home/hacker` 挂载各自 homefs 卷（卷名 = 用户 id） | A 写的文件 B 看不到，B 写的 A 看不到 |
| 客户机磁盘 | 每次启动用种子盘新建一份 overlay，互不共享 | A 在客户机 `C:\Lab` 写的标记文件，B 的客户机里不存在 |
| 容器网络 | `workspace_net` + iptables `WORKSPACE-NET` 链，末尾 `DROP` | A→B、B→A 的 6080/22/8000 全部 `BLOCKED(rc=11)`；解析得到对方 IP 但连不通 |
| 平台接口 | 容器名由 `get_current_user()` 推导，请求体里的 `user_id` 不参与 | A 启动请求里塞 `user_id=7064` 被忽略；A 停止只停掉自己的容器，B 的照常运行 |
| 工作区代理 | nginx `secure_link_hmac`：签名 = HMAC(secret, container_id) | A 的签名配 B 的 container_id → 404；匿名访问 B → 404；A 访问自己 → 200 |
| 危险挂载 | 只挂 `/nix`、`/run/dojo/sys` 与自己的 home | 容器内没有 docker socket，也看不到 `/var/homes`、看不到别的用户目录 |
| 出网 | 未授予 INTERNET 的学生会被从默认 bridge 断开 | 容器内解析平台库名 `db` 失败（不在同一网络），外网亦不可达 |

## 需要知道的一点：工作区 URL 是能力凭据

工作区地址形如 `http://<host>:4443/workspace/<container_id>/<hmac>/<port>/vnc.html`，
其中 `<hmac>` 是服务器用 `WORKSPACE_SECRET` 对 `container_id` 做的 HMAC-SHA256。实测：

- 把签名换成别人的 container_id → 404（签名与容器绑定，不能改指向）；
- 但**持有完整签名 URL 的任何人都能打开该桌面**（实测 B 会话、甚至未登录请求，带着 A 的完整 URL 都是 200）。

这意味着：只要学生不把这条 URL 转发给别人，环境就是私有的；一旦转发，对方在其环境重建前可以进入该桌面。
环境重建（停止/重启）会生成新的 container_id，旧 URL 立即失效。

如果需要进一步收紧，有两个可选改法（都属于平台侧改动，我可以按需实施）：

1. 给签名加一层会话绑定：把用户 id 一并纳入 HMAC 消息，并把用户标识放进一个由平台设置、HttpOnly 的
   cookie，由 nginx 一并参与校验；代价是跨设备/无 cookie 的场景（如直接复制链接到另一台机器）会失效。
2. 缩短能力有效期：目前 cookie `Max-Age=43200`（12 小时），可缩短到与单次会话一致，并让平台在
   轮换/退出登录时主动回收。

## 教师与管理员侧

平台管理员按设计可以看到所有正在运行的环境（平台管理 → 运行环境）并终止它们；课程教师可以在课程管理里
看到课程内的活动与实时进度。这属于角色权限设计，不是隔离缺陷。

## 核查方式

用两个学生账号（`2022211575` / `2022210194`）同时启动环境，然后在宿主机侧执行：

- `docker inspect` 对比容器 ID、IP、挂载卷；
- 容器内用 Python socket `connect_ex` 测试跨容器端口；
- 通过平台接口与工作区代理做跨用户请求，观察 HTTP 状态码；
- 在两边客户机与 home 目录写入标记文件，交叉检查是否可见。

脚本与输出见本次会话记录；核查完毕后已把两个测试环境停止。
