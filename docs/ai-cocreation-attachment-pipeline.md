# AI 共创附件处理约定

## 用户可见的契约

上传成功表示原始文件已持久保存。此时可以立即发送消息；本次上传的附件随本次消息引用，先前上传的资料可通过输入框旁的“引用资料”按本轮勾选。界面不展示“分析课件”任务。明确引用文件内容的生成在原文提取完成后自动继续；未引用资料的普通对话不等待文件索引或结构摘要。

“根据这份课件”等单文件指代必须随消息指定那份文件。若本次没有上传，也没有在“引用资料”中选择，发送时提示选择；不能擅自扩大为整门课程的全部资料。“根据课程全部资料”等明确要求课程整体来源的请求仍可读取课程资料集合。

如果文件没有可读取的正文，应明确告知用户需要上传可读取的版本，不得把模型摘要失败描述成上传失败。后台摘要失败时，已建立的原文索引仍然可用。

## 数据与执行边界

1. **附件**：`TeachingMaterials` 和不可变的 `TeachingMaterialRevisions` 保存文件身份、哈希与存储位置；`TeachingMaterialChunks` 保存原文片段及位置。聊天消息只保存附件引用。
2. **原文索引**：现存 `material.analyze` 作业类型承担兼容旧作业的正文提取与分段，不调用模型。成功后将 revision 标记为 `READY`。这一内部作业在任务中心和对话的前台活动状态中隐藏，并由 `teaching:material-index` 专用 Worker 直接从共享存储读取本地格式原件，核对材料与修订身份、路径、文件大小和 SHA-256，再执行转换、OCR 和分段。主站请求进程拒绝本地格式的索引提取，不能回退到主站占用聊天请求资源。旧版 PPT 逐页转换并核对可读正文；图片型 PPTX 在 XML 正文不足时逐页渲染识别，不能把页码标记当正文；PDF 核对总页数，对扫描页按需 OCR，不允许只识别前 20 页却声称整份就绪。超出页数或识别时间上限时明确失败，原件仍可重新导出或拆分后重试。
3. **后台摘要**：索引成功后以相同 revision 的幂等键创建 `material.enrich` 作业，由 `teaching:materials` 队列执行。它读取已经持久化的同版原文片段，不重新转换原件；可以补充摘要和章节候选，但只更新同一 READY revision 的分析元数据。失败不能使附件退回 FAILED，也不能阻塞聊天。
4. **对话与生成**：引用附件的请求保留原始文本和来源引用。首次上传、尚未随消息发送的附件会进入第一轮；之后仅本轮明确勾选的资料会作为引用。仅仅选择“课件”或“模拟演示”类型不会暗中引用整门课程的历史文件；明确要求“根据课程资料”时才读取课程资料集合。普通消息在前台任务变化时按当前执行链自动排队。需要正文的执行只等待原文索引，不等待后台摘要；索引失败时仅这条请求给出可理解的文件读取错误，原要求仍保存在任务中。明确选中的附件必须完整可读，不能跳过失败附件使用不完整来源生成。派生候选作品时，候选作品来源不会被资料上下文覆盖。
5. **呈现**：任务中心只呈现用户发起的聊天、生成与审批等任务。附件上传进度、原文提取和后台摘要属于附件状态，不是独立的用户任务。前台输入框的当前任务判断同样排除这两类作业。

## 验收边界

- 上传后立即发送引用附件的消息；消息成功入队，正文提取完成后自动继续。
- 同时上传多个 PPT/PDF 时，普通聊天队列仍可处理其他请求。
- 合成的 180 页旧版 PPT 在后台建立索引期间，浏览器消息仍能立即入队；最终索引须覆盖完整正文。扫描版 PDF 超过 20 页、图片型 PPTX 无 XML 文字时，也须确认末页已进入索引，不能静默截断或仅将页码当正文。
- 资料索引记录的执行模式须为 `source-index-worker`，主站不得提供本地格式的在线转换服务。大课件正在 OCR 时，聊天消息仍能由主站迅速接受；专用 Worker 可排队消化 OCR 工作。
- 五个并发上传与发送的独立会话，都应先返回前台消息接受结果，再由专用 Worker 依次完成各自原文；每份资料的末页文本必须存在，QA 后无残留资料和作业。
- 已在上一条消息引用过的附件不自动附到以后的每条消息；需要再次使用时可明确勾选，避免隐藏的等待依赖。
- 上次发送失败后若更换本轮勾选的资料，重发会产生新请求正文和幂等键，不复用旧引用。
- 模型摘要超时或格式错误时，已索引的附件仍可用于问答、生成和引用。
- 任务中心、对话任务状态和上传区都不显示“分析课件”的运行任务；用户能看到真正的上传错误和不可读取文件错误。
- 同一 revision 重试不会产生重复的后台摘要；新 revision 不覆盖旧 revision 的原文。
- 取消任务时重读数据库中锁定后的状态；已经完成取消的任务不会被浏览器随后的一次取消操作重新写成“等待取消”。没有执行租约却停留在等待取消的记录可安全收敛为已取消。

## 设计依据

这套实现借鉴 [DeepSeek Harness 的 jobs 子系统](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/jobs.md)对后台作业的归属与生命周期划分，以及 [Codex app-server 的附件接口](https://github.com/openai/codex/blob/main/codex-rs/app-server/README.md)将持久附件与对话消息分离的做法。[OpenAI 异步工具调用文档](https://developers.openai.com/api/docs/guides/async-tool-calling)也强调后台工作应由应用管理，当前对话可继续。这里采用本项目现有的 Flask、PostgreSQL、Redis Stream 和 Next.js 机制，并不宣称与上游代码实现相同。
