# Teaching slide deck

Use this skill when a teacher asks to create, revise, or package slides, a presentation, PPT, or courseware deck. Preserve the teacher's audience, duration, objectives, source material, constraints, requested delivery format, and exact meaning. Analysis or revision of an existing deck is not automatically a new-deck task.

## Delivery contract

- Honor an explicit page count before every default. Exact means exact; a range stays inside the range. With no page request, create 12–15 substantive slides and normally aim for 14.
- Count only complete teaching pages. A directory, blank page, placeholder, repeated divider, or title-only filler is not a substantive slide.
- Generate a useful speaker script for every slide, including the cover and summary. Store it separately from learner-visible text so the preview can synchronize it to the active page.
- If the teacher asks for a file, return an accurately named downloadable presentation or the closest supported format.

## Production workflow

1. Read all supplied material before designing. Separate source facts from reasonable teaching assumptions and keep terminology traceable.
2. Write a one-sentence deck promise, audience profile, learning objectives, prior-knowledge assumptions, and classroom timing.
3. Build the complete story map before rendering any page. Give each slide one purpose and a clear transition from the previous page.
4. For every slide plan learner-visible content, a visual relationship or activity intent, the evidence it uses, and the private speaker script.
5. Render varied page structures with consistent typography, spacing, color, and a recurring visual motif. Prefer meaningful diagrams, comparisons, timelines, evidence views, code walkthroughs, and learner actions over decorative cards.
6. Run content, visual, and teaching-flow quality gates. Treat the first render as a draft that must be inspected and repaired.

Use the detailed production and script patterns in `references/production-workflow.md` and `references/speaker-script.md`.

## Teaching arc

A normal deck should move through a coherent arc rather than a collection of pages:

1. Hook, relevance, and authorized scope.
2. Outcomes and prior-knowledge diagnosis.
3. Mental model and essential vocabulary.
4. Concepts in a deliberate causal sequence.
5. A complete worked example or authorized security case.
6. Evidence, comparison, process, code, or diagram pages.
7. Guided practice, learner decisions, and feedback.
8. Misconceptions, failure modes, and repair.
9. Retrieval, transfer, and a verifiable completion standard.
10. Summary and next action.

Across a normal 12–15 page deck, use at least four distinct structures from cover, concept map, comparison, process, timeline, case evidence, code walkthrough, worked example, activity, checkpoint, and summary. Scale this requirement for a teacher-requested short deck. Do not use the same title-and-bullets layout for most pages.

Keep visible text concise and concrete. Use detailed explanations, transitions, questions, expected answers, misconceptions, timing, and facilitation cues in the speaker script instead of shrinking them onto the slide. Never invent source claims, expose hidden answers, or provide instructions aimed at public systems.

## Quality gate

Before delivery verify:

- Page count follows the teacher's request or the 12–15 page default, and titles are unique.
- Every objective is taught, practiced, and checked.
- A normal deck includes a worked example or case, a visual relationship page, at least two learner checks, a transfer task, and a real closing summary.
- Every slide has a non-empty, page-specific speaker script that adds value rather than repeating visible bullets.
- Layouts are varied, text fits, contrast is readable in the authored theme, and no page is empty or visually underdeveloped.
- Page order forms a complete narrative and each script includes a usable transition to the next page.
